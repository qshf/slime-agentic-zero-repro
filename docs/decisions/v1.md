# V1 决策日志：极简 calculator agent + Qwen3-0.6B

## 做了什么
- `toy_rl/agent/calculator_agent.py`：多轮 agent rollout，Qwen3-0.6B 经 SGLang OpenAI 接口生成工具调用，程序化构造 tokens/loss_mask。
- `toy_rl/reward.py`：规则 reward_func（提取 `<answer>` 对比 label）。
- `scripts/{server_setup,start_sglang}.sh`：服务器环境初始化 + SGLang Docker 部署。
- `scripts/test_v1_rollout.py`：离线测（calculator/reward）+ 在线测（真实 rollout 的 loss_mask 段规则）。

## 关键决策（选了 X 不选 Y 的 why）

- **推理引擎用 SGLang 不用 vLLM**：核对源项目 `requirements.txt` 只有 `sglang-router>=0.2.3`，无 vllm 痕迹。用 SGLang 才能让 V6 平滑接上源项目的 rollout engine 形态。

- **SGLang 用 Docker 部署，走 OpenAI 兼容接口（端口 30000）**：对齐源项目 `agentic/agentflow/rollout.py` 的默认端口。agent 通过 HTTP 调独立推理服务——这正是源项目"rollout engine 是独立进程"的形态，V1 就先建立这个心智模型。

- **loss_mask 仍程序化按"段"打，不用真 tokenizer 的 offset**：V1 用字符级假 tokenizer，让 tokens/loss_mask 对应关系肉眼可读。核心教学点是"按谁生成的这段文字打 mask"（agent 段=1，tool 返回段=0），而非 tokenizer 细节。真 tokenizer 留到 V6 接 SGLang RolloutManager。

- **reward 先用规则匹配，不用 LLM-as-judge**：源项目 AgentFlow 用 Rewarder（LLM 判分），但 calculator 任务答案是确定数字，规则匹配够用且零额外调用。LLM-as-judge 留到主线二 A2（AgentFlow）——那才是它的"真实需求"。

- **generate 返回 (Sample, final_answer) 元组，reward 暂留 None**：V1 先把"多轮交互→样本"跑通，reward 由独立的 reward_func 算。V2 hook 化时再统一成源项目的 `reward_func(args, sample)->dict` 签名并填回 sample.reward。

## 待服务器验证（本地只跑通了离线部分）
- 离线测试（calculator + reward_func）本地 PASSED。
- 真实 rollout（Qwen3-0.6B 多轮 + loss_mask 段规则）需在 5090 上跑：
  1. `ssh 5090` → `bash scripts/server_setup.sh`（拉代码+建 venv+装 openai+验 V0）
  2. `bash scripts/start_sglang.sh`（起 SGLang 容器，等就绪）
  3. `python scripts/test_v1_rollout.py`（完整验证）

## 暴露的痛点（引出 V2）
- generate/reward 是写死调用的普通函数，主循环直接 import 它们——换 agent/任务要改代码。
- 没对齐 slime 的可插拔契约（`--custom-generate-function-path` 等）。
- → V2：把 generate/reward 做成可通过配置路径动态加载的 hook。
