## Context（为什么做 A2）

A1 MemAgent 的 loss_mask **全 1**（单引擎、无工具），教不了"模型输出 vs 工具返回"的**训练边界**——这是
README 问题 #2 的精华课。A2 = **AgentFlow**，引入 **Planner→Executor→Verifier** 多角色 ReAct 循环。

**教学核心（路线图钦定）= "executor token 不训练"**：
- **只有 Planner** 的 `plan()` / `generate_next_step()` 成为训练序列（`loss_mask=1`）；
- **Executor（生成工具命令 + 执行工具）/ Verifier（判 STOP/CONTINUE）/ final_output** 的生成 token
  **完全不进 training turns**——它们是"环境"，交给**固定引擎**跑，对 loss 零贡献。

这正是源在系统层的落地：**不训练的角色，交给不会变权重的固定引擎**；训练引擎只跑 planner 这个真正
要优化的策略。reward 相比 A1 的纯 boxed，新增 **LLM-as-judge 回退**（boxed miss 时固定引擎判官）。

**三模型分工（忠实源，不偏离）**——源 `engine_map`（rollout.py:136-144）用**三个不同的模型**：

| 角色 | 源引擎（端口） | 是什么模型 | 训练? |
|---|---|---|---|
| **planner**（plan/next_step） | router_port | **正在训练的 policy** | ✅ **唯一训练目标** |
| executor / verifier / final_output | 30000（generate_engine） | 固定 base 模型 | ❌ 纯环境 |
| **python_coder** 内部 | 30001（coder_engine） | **独立 coder 模型** | ❌ 纯环境 |

executor（base，不训练）出**自然语言**命令 `tool.execute(query="…")` → **python_coder 工具内部**再调
**独立 coder 模型**把 query 翻成 Python → subprocess 执行取 stdout。写代码那次 LLM 调用**不在** executor、
不进 trajectory——故"规划"（planner，训练）与"写代码"（coder，不训练）**解耦**，对齐源可分离性。若把
写代码塞进 executor，会把两个本可独立训练的关注点耦合掉、篡改训练目标，违铁律。nano 的 coder 模型 =
**外部 DeepSeek API**（OpenAI 兼容，密钥/base_url/model 走环境变量、不进 Args/不进 git）。

## 做了什么

**新增（镜像源 `agentic/agentflow/`，各文件 1:1 对齐角色）**：
- `toy_rl/agent/agentflow/memory.py`：`Memory`（action dict，几乎照搬源 `core/memory.py`）。
- `planner.py`：`Planner`——`plan` / `generate_next_step`（训练引擎，进 turns）+ `generate_final_output`
  （显式收固定引擎 chat_fn，不进 turns）。prompt 模板从源逐字搬。
- `executor.py`：`Executor`——`generate_tool_command`（固定引擎产 `tool.execute(query=…)`，正则抽**自然
  语言** query）+ `execute_command`（按 `tool_name` 在注册表里**真分发**到对应工具，见下"分发修正"）。
- `tools/base.py`：`BaseTool`——两工具共同契约（`tool_name`/`tool_description` + `async execute(query)`），
  镜像源 `tools/base.py`。
- `tools/base_generator.py`：`BaseGeneratorTool`——镜像源 `tools/base_generator/tool.py`：固定 base 引擎
  直接答 query（无 subprocess、纯环境、不训练；对齐源 engine_map `base_generator`→`generate_engine`）。
- `tools/python_coder.py`：`PythonCoderTool`——镜像源 `tools/python_coder/tool.py`：内部调**独立 coder
  模型（DeepSeek）** 把 query 翻成 Python（`preprocess_code` 抽代码块 + `_sanitize_code` 去危险调用）→
  `_run_code_in_subprocess` 子进程执行取 stdout。`deepseek_coder_chat_fn` 走环境变量（DEEPSEEK_API_KEY /
  CODER_BASE_URL / CODER_MODEL）。
- `verifier.py`：`Verifier`——`verificate_context` → `parse_conclusion`（照搬源 STOP/CONTINUE 解析）。
- `rewarder.py`：`Rewarder`——`compute_reward`（固定引擎判官 `VERDICT: True/False`，照搬源解析）。
- `solver.py`——**本版的星**：`Solver.solve` 编排 ReAct 循环，**只把 planner 两类调用 `_emit_turn`**
  （loss_mask=1），拼接进 sample。`extract_context_subgoal_and_tool`（源 formatters）折进本文件。
- `rollout.py`——薄适配器：造**三模型** chat_fn（planner→训练 SGLang / fixed→base SGLang / coder→DeepSeek）
  → 组装 Solver → 回填 Sample；`reward_func`（boxed 精确匹配 + `Rewarder` 回退）。boxed/is_equiv/strip_think
  复用 A1 memagent.rollout。
- `data.py`：4 条硬编码**多步计算** QA（`{prompt,label}`，需写段 Python 算、label 可 boxed 命中）。
- `stub_rollout.py`：离线 no-SGLang/no-DeepSeek stub，复用**同一个** `_build_solver`/`Solver.solve`，注入
  三个造假 chat_fn（planner 产 Context/Sub-Goal/Tool Name；fixed 产 `tool.execute` + STOP + `\boxed{label}`；
  **coder 打桩返回确定 Python 代码块，但 python_coder 真跑 subprocess**）。
- `scripts/test_a2_agentflow.py`：不变量 1-5（多轮结构 + executor token 不训练 + 只有 planner 进 turns
  + python_coder 真执行 + boxed reward + 闭环）。

**改动（都朝"更对齐源 + 零回归"方向）**：
- `mini_slime/args.py`：加 A2 专属字段 `af_planner_base_url/af_planner_model/af_fixed_base_url/

## 与 A1 MemAgent 的关键差异（A2 新引入的）

| 维度 | MemAgent（A1） | AgentFlow（A2） |
|---|---|---|
| 引擎 | 单引擎 | **三模型**（训练 planner / 固定 base executor·verifier·final / 独立 coder=DeepSeek） |
| 角色 | 只有 LLM 自己 | **Planner→Executor→Verifier** 多角色 ReAct |
| 工具 | 无工具 | python_coder（executor 出 NL 命令→工具内 coder 模型写 Python→子进程执行） |
| loss_mask | response 全 1 | **只有 planner 进 turns**；executor/verifier/final_output 根本不进 → 对可训练 token 零贡献 |
| reward | boxed + is_equiv | boxed + **LLM-as-judge 回退**（固定引擎判官，reward 稳定） |
| 多轮 | N 条独立记忆对话 | 1 plan + K next_step（每条独立训练序列） |

## 分发修正（2026-07-23，A2 收官后回补）

**问题**：初版 executor 只持单 `coder_tool`，`execute_command(tool_name, query)` 收了 `tool_name` 却
**从不使用**、无条件走 coder——是"保留参数名的假分发"，会让读者误以为已实现 tool_name→tool 路由，且与
源 `execute_command`（`_resolve_tool_mapping`→`_load_tool`→`tool.execute`）不符。

**修正**：恢复**真分发**——`Executor` 收 `toolbox: dict[str, BaseTool]`，`execute_command` 用
`_resolve_tool(tool_name)` 按名查表选实例（未命中回退第一个 + warning，对齐源"未知名回退
Base_Generator"）。新增 `base_generator` 工具（固定 base 引擎直接答），与 python_coder 一起注册——
对齐源 engine_map 的两工具。发现方式仍用 dict 注册（非 importlib 目录扫描），见偏离表。

**`generate_tool_command` 保留**（未删，尽管功能价值弱）：源两工具统一 `execute(query=...)`、无 per-tool
参数适配，故这次额外 LLM 改写在功能上确实冗余（源亦如此）。但保留它有两个压过冗余的理由——①**源保真**
（源有这步，本项目"复现中学"不为比源更省）；②它是**"executor token 不训练"的活教材**：一次固定引擎 LLM
调用、token 明确不进 turns，删了会抹掉训练边界的演示。故保留，注释改诚实（不再暗示它是承重管线步骤）。

**新断言**：`test_a2_agentflow.py:test_executor_dispatch` 直接构 Executor 挂两工具，验证不同 tool_name
走到不同工具（coder→subprocess `42` / base_generator→chat_fn 文本）、未知名回退不崩——证明分发真按
tool_name 生效。

## 测试为什么仍用同步 train_ray（同 A1）

`test_a2_agentflow.py` 的 `test_closed_loop` 调 `train_ray.py`（同步，≡ 源 train.py），不用 `train_async.py`。
理由与 A1 完全一致（见 a1.md「测试为什么用同步」一节）：train_ray 与 train_async 对 agent 等价、唯一区别是
gen(N+1) 的调度时机；异步正确性 + overlap 已由 V5 的 `test_v5_async.py` 专门担保。A2 只需验证 AgentFlow 产的
样本形态（loss_mask 边界 / turns 结构 / reward），用同步版是更干净的载体。

## 暴露的痛点（引出 A3）
- AgentFlow 单一 reward（boxed/judge）+ 固定 planner→单工具路由：教不了**多专家路由 + 多组件 reward**。
  → **A3 ToolOrchestra（仅 QA 路径）**：多专家路由 + 多组件 reward 组合（**主线二终点**）。
