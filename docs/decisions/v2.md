# V2 决策日志：custom generate/reward hook 化

## 做了什么
- `mini_slime/hooks.py`：`load_function(path)` 按 "module.func" 字符串 importlib 动态加载，逐行对齐源项目 `slime/utils/misc.py:9`。
- `toy_rl/agent/calculator_hooks.py`：把 V1 的 generate/reward 重构成源项目签名 `generate(args, sample)->Sample` / `reward_func(args, sample)->dict`；`Args` dataclass 承载配置（含 hook 路径）。
- `scripts/test_v2_hooks.py`：离线测（加载/错误路径/reward hook）本地 PASSED；端到端测待 SGLang。

## 关键决策（选了 X 不选 Y 的 why）

- **hook 加载逐行抄源项目 `load_function`，不自造机制**：源项目就是 `module_path.rpartition(".")` + `importlib.import_module` + `getattr` 三行。这是 slime 全部 `--custom-*-path` 的统一实现，简洁到没有简化空间。V2 的教学价值正是"框架如何不认识具体 agent 却能调它"——直接对齐最有说服力。

- **签名对齐 `(args, sample)`，不保留 V1 的 `(prompt, label)`**：源项目所有 hook 第一个参数都是 args（全局配置），第二个是 sample。V1 的自定义签名换 agent 就得改主循环；V2 统一签名后，主循环 `await generate(args, sample)` 对任何 agent 通用。这是 V3 闭环能"插进任意 agent"的前置。

- **reward 返回 dict 不返回 float**：源项目 `reward_func` 返回 dict（可承载多组件 reward，如 ToolOrchestra 的 correctness+cost+latency）。V2 只放 `{"reward": score}`，但用 dict 类型对齐，为主线二 A3 的多组件 reward 留好接口。

- **保留 V1 的 calculator_agent.py 不删**：V1 版作为"未 hook 化"的对照，教学上能直观看到 V1→V2 的签名演进。calculator_hooks.py 复用 V1 的 `calculator`/`_tokenize`/mask 常量，不重复实现。

- **Args 用极简 dataclass 不用 argparse**：源项目 args 是庞大的 argparse Namespace（几百个字段）。nano 只取 generate/reward 真正用到的 6-7 个字段，避免 argparse 噪声淹没 hook 概念。真 argparse 若主线三需要再引入。

## 重构（2026-07-20，落实"代码范式遵从源项目"铁律）

起因：审视 agent loop（调工具/执行/拼结果）时发现两个偏离源项目范式的糙点，休掉：

- **loop 曾被抄成两份**：V1 `calculator_agent.generate` 和 V2 `calculator_hooks.generate` 各写了一遍完整多轮 loop。源项目里 `rollout.py:104 generate()` 是**薄适配器**，真正的 loop 在 `core/solver.py:65 Solver.solve()`（一处）。→ 修法：loop 收进 `calculator_agent.run_agent_loop()`（唯一实现处），V1 入口和 V2 hook 都调它、只做"填 Sample"的薄适配，精确对齐 rollout.py→solver.solve 的分层。
- **元组返回 `(Sample, final_answer)`**：源项目 generate 只返回 `Sample`，最终答案放 `sample.metadata["final_output"]`。→ 修法：去掉元组，`generate()` 只返回 `Sample`；`Sample` 新增 `metadata` 字段（对齐源项目 `Sample.metadata`），承载 `final_output` 与 `turns`（对齐源项目 `train_metadata["turns"]` 的结构化按轮记录）。
- **工具分发无接缝**：正则解析 + 调 `calculator()` 焊死在循环体。→ 修法：抽 `TOOLS` 注册表 + `_dispatch_tool(name, arg)`，对齐源项目 `Executor.execute_command` 的分发角色，加工具 loop 不改。
- **保留的刻意简化（比源项目"更清晰"而非"更差"）**：字符级假 tokenizer（可读性）、单条增长对话里工具返回段直接打 `MASK_TOOL=0`（源项目是把工具结果丢进 Memory、作为下一轮 prompt 的 mask=0 段——语义等价：工具返回都不训练；nano 用扁平单序列换 loss_mask 肉眼可读，真 tokenizer/多序列 concat 留 V6）。

验证：离线测 + 打桩 loop（不连 SGLang）双通过——契约等长、prompt 段全 0、turns 正确、V1/V2 两入口复用同一 loop 且 reward=1.0。

## 工具层升级为 ToolRegistry（2026-07-20，借鉴 nano_hermes，锚点仍是 slime-agentic）

起因：用户本意是借鉴 nano_hermes_agent 的工具系统，把临时的 `TOOLS = {...}` dict + `_dispatch_tool()` 升级得更规整（有元数据、有"元数据→prompt"链、加工具不改 prompt）。

做了什么：新增 [toy_rl/agent/tools.py](../../toy_rl/agent/tools.py)，把工具从 agent loop 里分出来——`BaseTool`（对齐源 tools/base.py）/ `CalculatorTool`（V1 calculator 逻辑收进工具类）/ `ToolRegistry`。`calculator_agent.py` 建 `_REGISTRY` 单例，system prompt 用 `render_for_prompt()` 动态渲染工具清单，loop 里 `_dispatch_tool` → `_REGISTRY.execute_command`。

对齐 slime-agentic 的锚点（逐项）：
- `BaseTool(tool_name, tool_description, demo_commands)` —— 逐字段对齐源 tools/base.py。
- `ToolRegistry.available_tools` / `toolbox_metadata` —— 对齐源 `Planner._discover_tools` 的两个产物。
- `render_for_prompt()` —— 对齐源"把 available_tools/toolbox_metadata 注入 planner prompt 文本"（planner.py:85-86/116-117），**不进 tools=**。
- `execute_command()` 永不抛异常、返回纯字符串 —— 对齐源 `Executor.execute_command:225`。

次级借鉴 nano_hermes 什么 / 不借什么（准则：只借不与源冲突且更清晰的）：
- ✅ 借：单 registry 对象 + dispatch 接缝的**结构**（比手写 dict 规整）。
- ❌ 不借：`get_definitions → tools=` native tool-calling —— 破坏 RL 的 token/log_prob 保真度，违铁律。
- ❌ 不借：`tool_result()/tool_error()` 的 **JSON 信封** —— 源 `execute_command` 返回纯串/Any，套 JSON 就偏离源，故工具返回一律纯字符串。

唯一偏离（按铁律写明三要素）：
- ① 源怎么做：`Planner._discover_tools` 扫描 `tools_dir`，importlib 动态加载每个 tool.py，读 TOOL_NAME/TOOL_DESCRIPTION 组装元数据。
- ② 为何偏离：nano V1 仅 1 工具，目录扫描+importlib 是仪式，会淹没"工具系统"概念；改为构造 registry 时直接传 tool 实例列表。
- ③ 是否等价/何时补齐：等价（都产出 available_tools+toolbox_metadata+分发口）；`tools_dir` 文件系统发现暂缓到"多工具/多 agent"阶段。

兼容：保留模块级 `calculator = CalculatorTool().execute`，`run_agent_loop`/`generate`/`calculator_hooks` 签名与返回完全不变——纯内部重构，现有测试零改动。

## 暴露的痛点（引出 V3）
- 有了可插拔的 generate/reward，但还是手动一次次调用它们，没有编排多轮 `rollout→train→update_weights` 的循环。
- rollout 和 train 挤在测试脚本里，没有独立的 RolloutManager / Trainer 角色。
- → V3：mini_slime 的 rollout_manager + fake trainer + weight_sync，跑真正的多轮闭环并采集指标。
