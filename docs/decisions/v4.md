# V4 实施计划：Ray 化（actor 拆进程 + ray.get 同步点）

> 状态：**✅ 完成（5090 端到端 3/3；本地离线 3/3）**。
> 对应源项目锚点：`train.py:9-95`（ray 主循环 + 工厂装配）、`slime/ray/placement_group.py:79/132/181`
> （create_placement_groups / create_training_models / create_rollout_manager）、
> `slime/ray/rollout.py:440 @ray.remote class RolloutManager`、
> `slime/ray/actor_group.py:10 RayTrainGroup` + `train_actor.py:28 @ray.remote TrainRayActor`。

## Context（为什么做 V4）

V3 结束时的痛点（[v3.md](v3.md) 末尾，且已被实测坐实）：主循环**全串行**——5090 实测 `gen=43/27s`
而 `train/sync≈0s`，`generate` 跑 SGLang 时 trainer 空转、`train` 时推理引擎空转。单进程里
RolloutManager 和 Trainer 根本没法并行。

V4 做的：把两个角色**拆进独立进程**（Ray actor），主循环用 `.remote()` 发起、`ray.get()` 标注
同步点。**这一版本身仍是串行的**（`ray.get` 强制等待）——它不解决串行，而是把"角色分进程"
这层结构立起来，为 V5 的 `generate(N+1)` overlap `train(N)` 铺路。这正是路线图的痛点链：
V4 暴露"ray.get 强制等待"→ 引出 V5 异步。

## 源项目骨架（已读实证，V4 要对齐的形状）

装配三步（train.py:9-24）+ 主循环（train.py:65-93）：
```python
pgs = create_placement_groups(args)                                  # 分配 GPU bundle
rollout_manager, _ = create_rollout_manager(args, pgs["rollout"])    # 单个 @ray.remote actor
actor_model, critic_model = create_training_models(args, pgs, rollout_manager)  # RayTrainGroup
actor_model.update_weights()                                         # 训练前先同步一次权重
for rollout_id in range(args.start_rollout_id, args.num_rollout):
    rollout_data_ref = ray.get(rollout_manager.generate.remote(rollout_id))  # 产数据（另一进程）
    ray.get(actor_model.async_train(rollout_id, rollout_data_ref))           # 训（另几个进程）
    actor_model.update_weights()                                             # 同步权重回引擎
```

三个角色的进程/装饰器形态（Explore 已核对）：

| 角色 | 源位置 | 装饰器 | 进程 | nano 对应 |
|---|---|---|---|---|
| `RolloutManager` | rollout.py:440 | `@ray.remote` | 独立 1 个 | 单 actor，`.generate.remote(id)` |
| `RayTrainGroup` | actor_group.py:10 | 无（本地包装类）| 无（本地对象）| 本地类，持 N 个 worker handle |
| `TrainRayActor`（各 rank）| train_actor.py:28 | `@ray.remote(num_gpus=1)` | 每 rank 一个 | fake trainer 的 actor 壳 |

- `RayTrainGroup.async_train` 返回 **list[ObjectRef]**（每 rank 一个），`update_weights` 内部
  `ray.get` 广播 rank0→其余。这是 DP fan-out 的形状。
- 数据流：`generate.remote` 产 train_data dict → ObjectRef → 传给 `async_train` → 每个 worker
  在自己进程里 `ray.get(rollout_data_ref)` 取数训练。

## V4 要建的文件（nano `mini_slime/ray/`，镜像源 `slime/ray/`）

### `mini_slime/ray/placement_group.py` — 装配工厂（对齐源三个工厂函数名）
```python
def create_placement_groups(args) -> dict:
    # 对齐源 create_placement_groups：分配资源 + 让 ray 就绪。
    ray.init(num_cpus=..., num_gpus=0, ignore_reinit_error=True)
    return {"actor": None, "rollout": None}   # 见偏离：nano 无 GPU bundle，占位保持形状

def create_rollout_manager(args) -> handle:
    # 对齐源 create_rollout_manager：把 V3 的 RolloutManager 包成 @ray.remote 单 actor。
    Actor = ray.remote(num_cpus=1, num_gpus=0)(RolloutManager)
    return Actor.remote(args)

def create_training_models(args) -> tuple[RayTrainGroup, None]:
    # 对齐源 create_training_models：actor_model = RayTrainGroup(...)；critic 砍掉返回 None。
    return RayTrainGroup(args), None
```

### `mini_slime/ray/actor_group.py` — RayTrainGroup + TrainRayActor
```python
@ray.remote(num_cpus=1, num_gpus=0)      # 对齐 train_actor.py:28（源是 num_gpus=1，nano fake 无 GPU）
class TrainRayActor:
    def __init__(self, rank, world_size): self.rank, self.world_size = rank, world_size
    def init(self, args): self._trainer = Trainer(args)     # 复用 V3 Trainer（不重写训练逻辑）
    def train(self, rollout_id, rollout_data): return self._trainer.train(rollout_id, rollout_data)
    def update_weights(self): self._trainer.update_weights(); return self._trainer.weight_version
    def get_weight_version(self): return self._trainer.weight_version
    def pid(self): return os.getpid()

class RayTrainGroup:                      # 对齐 actor_group.py:10（本地包装，非 ray.remote）
    def __init__(self, args, num_nodes=1, num_gpus_per_node=1):
        world_size = num_nodes * num_gpus_per_node          # V4=1（DP=1）
        self._actor_handlers = [TrainRayActor.remote(r, world_size) for r in range(world_size)]
    def async_init(self, args):  return ray.get([a.init.remote(args) for a in self._actor_handlers])
    def async_train(self, rollout_id, ref):                 # 返回 list[ObjectRef]，对齐源
        return [a.train.remote(rollout_id, ref) for a in self._actor_handlers]
    def update_weights(self): return ray.get([a.update_weights.remote() for a in self._actor_handlers])[0]
    def weight_version(self):  return ray.get(self._actor_handlers[0].get_weight_version.remote())
    def pids(self):            return ray.get([a.pid.remote() for a in self._actor_handlers])
```

### `mini_slime/train_ray.py` — V4 ray 同步主循环（对齐 train.py:65-93）
逐句对齐源：`create_placement_groups → create_rollout_manager → create_training_models →
async_init → update_weights（初始）→ for: ray.get(generate.remote) / ray.get(async_train) /
update_weights`。采集与 V3 **同名**的每轮指标（gen/train/sync_time、reward_mean、
tokens_per_rollout、weight_version），使 V3↔V4↔V5 可直接对照。

### 复用 V3 不改：`rollout_manager.py`（RolloutManager 保持普通类，V4 在 create 时用
`ray.remote(RolloutManager)` 包成 actor——普通类照样能被 V3 单进程 train.py 用）、`trainer.py`
（Trainer 逻辑被 TrainRayActor 壳复用，一行不改）、`weight_sync.py`、`args.py`。

### 离线测试用的 no-SGLang stub hook：`toy_rl/agent/stub_hooks.py`
`generate(args, sample)` 直接构造一段假 trajectory（不连 SGLang），`reward_func` 规则打分。
用途：本地跑通 **ray 装配/进程/ObjectRef 流** 而不需要 SGLang（rollout 在 actor **独立进程**里，
主进程 monkeypatch 不到它，故改用"换 hook 路径"——这恰好演示了 V2 hook 可插拔的价值）。

## 偏离说明（按铁律，三要素逐条写明）

| 偏离点 | ①源怎么做 | ②为何偏离 | ③等价性/何时补齐 |
|---|---|---|---|
| **无 GPU placement group** | `create_placement_groups` 分配 `{"GPU":1,"CPU":1}` bundle，用 `PlacementGroupSchedulingStrategy` 把 actor/engine 钉到 bundle | nano trainer 是 fake（CPU、不占 GPU）；SGLang 已在**独立 docker** 里，不归 ray 调度 | actor 分进程的语义等价（ray actor 本就独立进程）；真 GPU bundle 分配留主线三 V6/V7 |
| **`ray.init()` 进程内启动** | 源用 `ray start --head` 预起集群 + `ray job submit` 提交 | nano 单机、单脚本，`ray.init(num_gpus=0)` 更简单直观 | 语义等价（都连到一个 ray runtime）；多机集群留后续 |
| **world_size=1（DP=1）** | 源 `num_nodes*num_gpus_per_node` 个 TrainRayActor rank，`update_weights` 广播 rank0→其余 | fake trainer 无真并行必要；先看清"group→workers dispatch"形状 | RayTrainGroup 的 list[ObjectRef] 结构已保留；多 DP 真广播留主线三 |
| **fake trainer/权重同步** | 源 TrainRayActor 跑真 FSDP/Megatron + 真权重广播回 SGLang | 沿用 V3：主线一聚焦编排骨架非训练数学 | 角色/签名/数据契约等价；真 backend 留主线三 V6-V9 |
| **RolloutManager 构造时包 actor**（非 `@ray.remote` 装饰类）| 源直接 `@ray.remote class RolloutManager` | nano 要让**同一个类**既能被 V3 单进程用、又能被 V4 包成 actor，故用 `ray.remote(cls).remote()` 而非装饰器 | 语义等价（都是 ray actor）；更清晰（一份类两种用法，不重写） |

**次级借鉴 nano_hermes**：本版无需借（ray 编排源项目已足够清晰）。

## 实际结果（2026-07-21 实现后补）

**建成的文件**：`mini_slime/ray/{placement_group,actor_group}.py`（装配工厂 + RayTrainGroup/
TrainRayActor）、`mini_slime/train_ray.py`（ray 同步主循环）、`toy_rl/agent/stub_hooks.py`
（离线 no-SGLang stub hook）。验证 `scripts/test_v4_ray.py`。加 `ray>=2.5` 依赖。

**实现时对计划的两处落定（都朝源更靠拢 / 更清晰）**：
1. **RolloutManager 加一个 `pid()` introspection 方法**（rollout_manager.py）：供测试确认 actor 在独立
   进程。V3 单进程用不到，不改任何数据流——最小侵入。
2. **含训练前的初始 `update_weights()`**（对齐源 train.py:26 "always update weight first"）：故
   `weight_version == num_rollout + 1`（V3 是 num_rollout，无初始同步）。这是忠实源的一个真概念
   （让推理引擎从训练侧初始权重起步），测试断言相应改为 num_rollout+1。
3. **离线测试改用"换 hook 路径"而非 monkeypatch**：rollout 跑在 actor 独立进程，主进程 patch 不到，
   故 `--offline` 把 `custom_generate_function_path` 指到 stub_hooks——恰好实证了 V2 hook 可插拔的价值。

**离线验证**（本地 mac，ray CPU actor）：`python scripts/test_v4_ray.py --offline` → **3/3 通过**
（separate_processes / objectref_flow / full_loop）。实测 `main=4962 rollout=5132 trainer=5131`
三者不同进程。V0/V2/V3 回归全绿（加 pid() + __init__.py 未破坏）。

**服务器端到端验证**（5090 真 SGLang + ray，2026-07-21）：`uv run python scripts/test_v4_ray.py`
→ **3/3 通过**。实测：
```
main_pid=4164446 rollout_pid=4169275 trainer_pids=[4169194]   # 三者独立进程 ✓
[rollout 0] gen=37.802s train=0.0053s sync=0.0035s | reward_mean=1.000 tokens=1355 weight_v=2
[rollout 1] gen=28.850s train=0.0052s sync=0.0020s | reward_mean=1.000 tokens=1060 weight_v=3
```
**关键观察（引出 V5）**：分了进程，`gen`（28-37s）仍全程主导、`train/sync≈0.005s`——`ray.get`
把 rollout 和 train 锁成严格串行。注意 train_time 从 V3 的 0.0000s 变成 0.005s：这正是 ray 跨进程
IPC 的**新增成本**（V3 单进程内调用几乎零成本）。"分了进程却仍串行"就是 V5 要 overlap 的靶子。

## 指标输出（V4 采集，与 V3 同名以便对照）
每轮：`gen_time` / `train_time` / `sync_time` / `reward_mean` / `tokens_per_rollout` / `weight_version`。
**关键观察点**：V4 仍是 `ray.get` 串行——`gen_time` 应与 V3 同量级（串行没变），但 rollout 和 train
现在在**不同进程**。这个"分了进程却仍串行"就是 V5 要 overlap 的靶子。

## 验证
`scripts/test_v4_ray.py`（对齐 v4 计划）：
1. **分进程**：`rollout_manager` actor 的 pid、`TrainRayActor` 的 pid、主进程 pid **两两不同**。
2. **闭环**：跑 `num_rollout` 轮，metrics 字段齐全、类型对；`weight_version == num_rollout`；
   reward_mean ∈ [0,1]；train_data 契约（len 对齐 batch_size、每条 tokens/loss_mask 等长）。
3. **ObjectRef 流**：`async_train` 返回 list[ObjectRef]（可 `ray.get`），长度 == world_size。
- 本地离线：`--offline` 用 stub hook（不连 SGLang）跑通全套 ray 装配（mac 上 ray CPU actor）。
- 服务器端到端：5090 真 SGLang + ray 跑 `uv run python scripts/test_v4_ray.py`。

## 暴露的痛点（引出 V5）
- `ray.get(generate.remote(id))` 和 `ray.get(async_train(...))` 严格串行：rollout N+1 必须等
  train N 完全结束才开始。分了进程，`ray.get` 的位置却把并行度锁死。
- → **V5 同步 vs 异步**：在 train N 之前就 `generate.remote(N+1)` 提前发起下一轮 rollout，
  overlap 掉 train 的时间；`update_weights` 改按 interval。断言异步版总耗时 < 同步版。

## 范围外（V4 不做）
- 不做异步 overlap（V5）。不做真 GPU 调度 / 真训练 / 真权重广播（主线三）。
- 不碰 V1/V2/V3 已定稿的 agent loop / Sample / hook 签名 / RolloutManager·Trainer 内部逻辑。
