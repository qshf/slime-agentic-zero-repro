# V5 实施计划：同步 vs 异步（提前发起 rollout N+1 overlap train N）—— 主线一承诺终点

> 状态：**✅ 本地离线通过（async 1.492s < sync 2.018s，saving 0.526s；V0/V2/V3/V4 回归全绿）；待服务器端到端**。
> 对应源项目锚点：`train.py`（同步）vs `train_async.py:29/31/34/39/42/62`（异步主循环 + "改 ray.get 位置"）。

## Context（为什么做 V5）

V4 结束时的痛点（[v4.md](v4.md) 已实测坐实）：分了进程，主循环仍**严格串行**——`ray.get(generate.remote(N))`
和 `ray.get(async_train(N))` 顺序执行，rollout N+1 必须等 train N 完全结束才开始。5090 实测 `gen=28-37s`
全程主导、`train/sync≈0.005s`。`ray.get` 的**位置**把并行度锁死。

V5 做的：把 `generate.remote(N+1)` 在 train N **之前**发起，让下一轮 rollout 与本轮 train **overlap**；
`update_weights` 改按 interval 同步（换权重前先 sync 掉在途 generation）。忠实镜像源 `train_async.py`
的"改 `ray.get` 位置"手法（源注释：*"note that for async training, one can change the position of the
sync operation(ray.get)"*）。

## 源项目骨架（train_async.py，V5 对齐的形状）

```python
actor_model.update_weights()                                              # 训练前初始同步（同 V4）
rollout_data_next_future = rollout_manager.generate.remote(start_rollout_id)  # 预取 rollout 0
for rollout_id in range(start_rollout_id, num_rollout):
    if rollout_data_next_future is not None:                              # sync 上一次 generation
        rollout_data_curr_ref = ray.get(rollout_data_next_future)
    if rollout_id + 1 < num_rollout:                                      # 提前发起下一轮（overlap 核心）
        rollout_data_next_future = rollout_manager.generate.remote(rollout_id + 1)
    ray.get(actor_model.async_train(rollout_id, rollout_data_curr_ref))  # train N 与 gen N+1 并行
    if (rollout_id + 1) % update_weights_interval == 0:                   # 按 interval 同步权重
        rollout_data_curr_ref = ray.get(x) if (x := rollout_data_next_future) is not None else None
        rollout_data_next_future = None                                   # 换权重前先 sync 在途 gen
        actor_model.update_weights()
```

**已核对的关键前提**：任意时刻 rollout actor 上**最多一个** generate 在途——gen(N+1) 只在 gen(N) 被
`ray.get` 取走后才发起。故 overlap 是 gen(N+1)@rollout进程 与 train(N)@trainer进程 的**跨进程真并行**，
无需担心 ray async actor 并发。

## 关键设计洞察（V5 的核心难点）

源里 train 是真 FSDP/Megatron 一步（秒级），overlap 省真 wall-clock；但 nano 的 Trainer 是 fake，
`train≈0.005s`——**若 train≈0，overlap 无可省，异步 == 同步，断言必失败**。同理单 rollout actor 上
gen 天然串行，只有当 train 消耗真实/模拟时间、且 gen 提供一个可藏 train 的时间窗时，overlap 才可观测。

故引入两个"模拟耗时"旋钮（`args.py`，默认 0.0 → V3/V4 零影响）：
- `fake_train_seconds`：`Trainer.train()` 里 `time.sleep()` **代表**训练一步的计算 wall-clock。
- `fake_gen_seconds`：离线 stub gen 的 `asyncio.sleep()` **代表** SGLang 推理耗时（服务器真 SGLang 时=0）。

## 偏离登记（按铁律三要素）

| 偏离点 | ①源怎么做 | ②为何偏离 | ③等价性/何时补齐 |
|---|---|---|---|
| **`fake_train_seconds` sleep** | train 是真 FSDP/Megatron 一步（秒级计算） | fake trainer 无真梯度→train≈0，overlap 无可省、断言无法成立 | sleep 忠实代表训练一步的 wall-clock；真 backend 耗时留主线三 V6-V9 |
| **`fake_gen_seconds` sleep**（仅离线 stub） | gen 是真 SGLang 多轮推理 | 离线无 SGLang→gen≈0，无时间窗藏 train | 代表推理耗时；服务器路径此值=0 走真 SGLang |
| **复用 train_ray.py 作同步基线**（不建 train_sync.py） | 源同步文件叫 `train.py` | nano `train_ray.py`（V4 建）已扮演源 train.py 角色，另建 train_sync.py 会与它重复 | 语义等价且更清晰（对齐源命名 train.py↔train_async.py）；roadmap 草稿名 "train_sync.py" 作废 |
| **无 critic 分支 / 无 eval / 无 save** | train_async.py 有 use_critic、save_interval、eval_interval 分支 | 按路线图砍 critic（GRPO 式）；eval/save 非主线一骨架 | 主循环 overlap 骨架等价；这些分支主线二/三按需补 |
| **fake trainer / 权重同步 / world_size=1** | 真训练 + 真权重广播 + 多 DP rank | 沿用 V3/V4（主线一聚焦编排骨架） | 角色/签名/数据契约等价；真 backend 留主线三 |

**次级借鉴 nano_hermes**：本版无需借（源 train_async.py 已足够清晰）。

## 实际结果（2026-07-22，本地离线）

`python scripts/test_v5_async.py --offline`（mac，ray CPU actor，num_rollout=3、gen=0.1s/条、train=0.2s/轮）→ **PASSED**：
```
--- 同步基线 (train_ray) ---
[rollout 0] gen=0.506s train=0.208s ...   [1] gen=0.203s train=0.206s ...   [2] gen=0.204s train=0.204s ...
--- 异步 (train_async) ---
[rollout 0] wait_gen=0.393s train=0.202s   [1] wait_gen=0.000s train=0.205s   [2] wait_gen=0.000s train=0.203s
sync_total=2.018s  async_total=1.492s  saving=0.526s (理论≈0.400s)
```
**关键观察**：异步 rollout 1/2 的 `wait_gen=0.000s`——gen(N+1) 早在上一轮 train(N) 期间就在 rollout 进程跑完了，
主循环取时零等待。这就是 overlap 的直接证据。saving≈(num-1)*fake_train_seconds，异步把除首轮外每轮 train 都藏进了
gen 时间窗。V0(5/5)/V2(offline)/V3/V4 回归全绿（默认 fake_*_seconds=0，不受影响）。

**服务器端到端**（待跑）：`git fetch origin && git reset --hard origin/v5 && uv run python scripts/test_v5_async.py`
（真 SGLang gen + fake_train_seconds=5.0）。因 SGLang gen 方差大（V4 实测 28-37s），服务器以**观测报告**为主
（对齐 V4 对服务器计时的处理），离线为确定性权威断言。

## 暴露的痛点（主线一终点 → 主线二起点）
- 异步 overlap 只藏了 train N 的**计算**时间；真实系统里"train 用的是 gen(N) 的旧权重、gen(N+1) 已在跑"
  会引入 **off-policy staleness**（数据比权重旧一步）——这是 async RL 的固有权衡，源项目 update_weights_interval
  就是调这个新旧度的旋钮。nano fake reward 感知不到 staleness，记录在此，主线二真 agent + 真 reward 时会显现。
- 主线一（V0-V5 系统骨架）到此打通：Sample→generate→reward→trainer→update_weights→引擎的数据链、Ray 分进程、
  同步↔异步 overlap 全部立起。→ **主线二 A1 MemAgent**：把自造 toy calculator agent 换成第一个真实 agent。
