# V8.2 · 多卡 Megatron（TP × PP × CP）—— 迭代计划

> 状态：**计划待审**（2026-08-10）。分支 `v9`（V8 已在 `v8` 收官）。
> 一句话：**硬件前提变了** —— V8 那三条「单卡实测硬阻断」的偏离（gloo / PP / CP）在 4 卡机上全部不再成立，
> 本版把它们逐条退休，把 Megatron 的三根轴补齐。
> **本计划的关键可行性断言已在 4 卡 5090 实测**（见 §1），不是纸面推导。

---

## 0. 为什么现在做（痛点承接 + 前提变化）

V8 收官时留了三条偏离，理由**都是「单卡物理阻断」而非「不重要」**：

| V8 偏离 | 当时理由（实测） | 4 卡机上还成立吗 |
|---|---|---|
| **#1** 通信后端 gloo 而非 NCCL | 单卡多 rank 被 NCCL 硬拒（`Duplicate GPU detected: rank 0 and rank 1 both on CUDA device 80`） | ❌ **不成立** → 退休 |
| **#3a** PP 不实现 | PP 传激活需 CUDA p2p，**gloo 不支持**（`gloo::IoException writev Bad address`） | ❌ **不成立** → 退休 |
| **#3b** CP 不实现 | 单卡 CP=1 等于没开，**无可验内容** | ❌ **不成立** → 退休 |
| #3c EP 不实现 | gloo 无 all_to_all；**且 Qwen3-0.6B 是 dense 无 expert** | ✅ **仍成立**（模型没有 expert，换 MoE 模型才有意义）→ 维持 |

所以 V8.2 不是「再做一遍 V8」，而是**在同一份 loss 数学上补齐另外两根并行轴**，
并顺带获得 V8 拿不到的东西：**真实的通信后端（NCCL）**，这也是 V9 吞吐实验的前置
（V8 文档已明确「本版不做吞吐断言，gloo 走 TCP，留 V9」）。

### 三根轴切什么（本版教学核心）

| 轴 | 切什么维度 | 通信在哪 | 边界 |
|---|---|---|---|
| **TP**（V8 已做） | 参数的**行/列**（层内） | 层内部：col→row 之间 all-reduce **激活** | 单层可跨卡 |
| **PP**（本版新） | **层**（模型纵向切成 stage） | **stage 边界**：p2p send/recv 激活 | 通信量最小，但有 **bubble** |
| **CP**（本版新） | **序列**长度维 | attention 内部：ring / all-gather 交换 **KV** | 长序列不再受单卡显存限制 |

一句话对照：**TP 切「一层里的矩阵」、PP 切「层的列表」、CP 切「token 的序列」**。
三者正交，源里可同时开（`tp × pp × cp × dp == world_size`）。

## 1. 4 卡可行性 —— 已实测（2026-08-10，`ssh 5090`）

环境：4× RTX 5090（sm_120，各 32G），容器镜像 **`agentic-rl-infra-lab:fa2-mcore`**
（TE 2.17 + megatron-core 0.18.2 + FA2 2.8.3 + accelerate，torch 2.11+cu130；
2026-08-10 镜像收敛后的**唯一**镜像，配方与验收见 [v8-5090-followup.md](v8-5090-followup.md) §4。
本节首轮实测时用的是 `te-cudnn-system-spike` + 临时装 FA2 的 `--rm` 容器，两者数值逐位相同）。
拓扑 `nvidia-smi topo -m`：

```
GPU0  GPU1  GPU2  GPU3
GPU0   X   NODE  SYS   SYS      ← 0-1 同 NUMA node（PCIe 同 root complex）
GPU1  NODE  X    SYS   SYS
GPU2  SYS  SYS    X   NODE      ← 2-3 同 NUMA node
GPU3  SYS  SYS   NODE  X
```

**无 NVLink**，跨组走 SYS（PCIe root complex 之间）。这直接决定 §3.4 的 rank 映射策略。

| # | 实测项 | 结果 | 对 V8.2 的含义 |
|---|---|---|---|
| 1 | **NCCL 双 rank 双卡 all_reduce** | ✅ `[3,3,3,3]` 正确 | **偏离 #1 可退休** |
| 2 | **NCCL CUDA p2p `send`/`recv`** | ✅ rank1 收到 `[7,7,7,7]` | **PP 的物理前提成立**（gloo 这里直接 abort）→ 偏离 #3a 可退休 |
| 3 | **`mpu.initialize_model_parallel(TP=1, PP=2)`** | ✅ `pp_rank=0/1` | PP 并行组能建 |
| 4 | **`mpu.get_embedding_group()`** | ✅ `[0, 1]` | **tie 模型跨 first/last stage 的梯度规约通路已就位**（见 §3.3，本版最硬的正确性点） |

> **~~待实测~~ 已实测（2026-08-10，两轮）**：CP=2 的 ring attention 在 sm_120 上**可用，且与 packing 可组合** ——
> 前提是 attention 后端选 **flash（FA2）** 而非 fused（cuDNN）。完整证据见 **§1.1**。

### 1.1 CP × FA2 varlen 实测 —— **可组合，但后端选择是正确性前提**（本轮推翻上一轮的悲观结论）

这一节被改写过两次，改写过程本身就是教训，故保留经过：

- **第一轮**（只测了 fused 与 unfused 两个后端）得出「CP 与 packing 不可组合，CP 只能走 fused + padding(BSHD)」。
- **第二轮**（读源项目 PP/CP 实现时发现线索）补测 **flash 后端**，全部判据转绿 —— **第一轮的结论作废**。

**线索来自源项目自己的文档**：`docs/zh/developer_guide/debug.md:15` 写着「在某些版本的 te 里，
megatron 需要 `--attention-backend flash`，来强制使用 flash attention，从而避免 **CP 下 fused attention 的数值不稳定**」，
且源**所有** megatron 训练脚本的 `MISC_ARGS` 都带这一行（`run-qwen3-4B.sh:139`、`run-deepseek-r1.sh`、`run-glm4-9B.sh` …）。
**源遇到过同一类问题，它的解法是绕开 fused 后端，而不是放弃 CP 或放弃 packing。**
第一轮之所以漏掉，是因为把 TE 的后端选择当成了二元的「fused / 不 fused」——
实际是三选一，而漏掉的第三个恰好是源在用的那个。

**三后端实测矩阵**（复现脚本 [`scripts/probe_v8.2_cp_packing.py`](../../scripts/probe_v8.2_cp_packing.py)，跑法见其 docstring）：

| 后端 | C1 单段 THD vs BSHD forward | C2 同上 backward | C4 CP=2 BSHD | C4 CP=2 THD |
|---|---|---|---|---|
| **fused**（cuDNN 9.25） | `max_abs_diff=0.000e+00` ✅ | **`dq` cosine `0.356`、ratio `24.7×` ❌** | PASS | **`thd_second_half_lse_correction` assert ❌** |
| **flash**（FA2 2.8.3） | `max_abs_diff=0.000e+00` ✅ | **`dq` cosine `1.00000000`、ratio `1.00×` ✅**（dk/dv `0.99999988`） | PASS `\|dq\|=106.62` | **PASS `\|dq\|=102.66` finite ✅** |
| **unfused**（O(N²) 参考） | `0.000e+00` ✅ | cosine ≥ `0.99999994` ✅ | ❌ 不支持 CP | ❌ 不支持 CP |

C3（vs unfused 参考）对 flash 的 bshd/thd 两组给出**逐位相同**的数字（`dq` 0.99996847 / `dk` 0.99999839 / `dv` 1.00003910，
差异均 bf16 舍入量级），独立佐证 C1/C2。

**TE 的后端选择怎么控制**：`NVTE_FLASH_ATTN` / `NVTE_FUSED_ATTN` / `NVTE_UNFUSED_ATTN` 三个 env。
megatron 的 `--attention-backend flash` 正是翻译成 `FLASH=1, FUSED=0, UNFUSED=0`
（mcore `language_module.py:124-140` 的 `check_and_set_env_variable`）。

**后端是被断言的，不是被假设的**（探针加固后复跑，2026-08-10）：env 表达的是**请求**，
TE 可能按 dtype/head_dim/CP/硬件否掉它，故上表每一行的后端都由探针从 TE 自己的
`_attention_backends` 缓存读回并与 `TAG` 断言一致，实测自报值：

| 请求 | TE 实选（探针 C0 读回） |
|---|---|
| `FLASH=1` | **`FlashAttention(2.8.3)`** ← 版本号直接自证是 FA2 而非 FA4 |
| `FUSED=1` | `FusedAttention(NVTE_Fused_Attn_Backend.NVTE_F16_arbitrary_seqlen)` |
| `UNFUSED=1` | `UnfusedDotProductAttention` |

`CP=2` 的两行也各自内联报告后端，实测 BSHD 与 THD **都是** `FlashAttention(2.8.3)`
（TE 按 `attention_params` 缓存选择，qkv_format 不同会重选，故必须分别读）。
**negative control**：故意令 `TAG=flash` 而 env 请求 fused，探针在 C0 即退出并报
`❌ 后端不符` —— 证明这条断言有判别力，不是装饰。

**仍然成立的两条约束**（与后端无关）：

| # | 约束 | 证据 |
|---|---|---|
| **1** | **CP 只有 TE 后端支持**，local spec 直接 assert 死 | `dot_product_attention.py:57-59`：`assert config.context_parallel_size == 1, "Context parallelism is only supported by TEDotProductAttention!"` |
| **2** | **unfused 不能作 CP 的 workaround** | `CP=2` 下 BSHD/THD 双双 `ValueError: No dot product attention backend is available` |

**已作废的两条**（原 #2/#3，都只针对 fused 内核）：TE 对 sm_120 关掉 THD+CP 的 packed-LSE
（`context_parallel.py:1670-1674`）、以及「patch 掉那个 carve-out 会跑通但算错」——
**走 flash 后端根本不经过这两条路径**。原 #4（TE#3333 的 THD backward 坏）依然是真的，
但它是 **cuDNN fused 内核专属**，不构成对 CP 或 packing 的约束。

> **不要去 patch 上游 carve-out**：这条建议保留且理由更强了 —— 当时的诱惑是「改一行就能跑」，
> 现在看正确做法是换后端。**遇到上游护栏时，先找官方绕行路径，再考虑拆护栏**。

**对 V8.2 的影响（相较第一轮全部反转）**：

1. **G3（CP 门）走 flash + THD(packing)**，与 V7.6 主线的 attention 后端一致，不需要单独的 padding 路径。
2. **不需要硬断言 CP × packing 互斥** —— 该组合是对的。真正该断言的是**后端**：
   `context_parallel_size > 1` 时必须是 flash，落到 fused 上要报错（fused 会**静默算错**，正是最该用断言堵的）。
3. **仍需给 `MegatronTrainer` 加 TE spec 分支**（约束 #1 不变，local spec assert `cp==1`）。这条第一轮就识别到了，不受影响。

> **教学价值（本轮更新）**：第一轮的教训是「forward 相等 ≠ backward 相等」，与 V8 坑③、
> v8-5090-followup §3 的假阴性同源，这条依然成立。
> **第二轮新增一条更值钱的**：**测出「不行」时，先确认自己穷举了配置空间** ——
> 第一轮的三层推理（CP 只能 TE → TE 的 THD 在 sm_120 坏 → 故 CP 必须 padding）
> 每一步单独看都有实测支撑，**结论却是错的**，因为第一步到第二步之间漏了一个后端。
> 而源项目的默认配方里就写着答案。**读源比自己推理便宜。**

## 1.5 源项目怎么配并行 —— 4 卡 / <4B 的选型结论（2026-08-10 通读源配置后补）

写码前先看源自己怎么配（铁律）。三个事实决定了 nano 的选型：

### 事实一：`--train-backend` 是二选一，不是可组合的

源 `arguments.py:1430`：`choices=["megatron", "fsdp"], default="megatron"`。

| backend | 有哪些并行轴 | 证据 |
|---|---|---|
| **fsdp** | **只有 DP**。`_setup_device_mesh()` 注释直书 *"Pure data parallelism"*，`init_device_mesh("cuda", mesh_shape=(self.dp_size,), mesh_dim_names=("dp",))` | `fsdp_utils/actor.py:186-203` |
| **megatron** | TP × PP × CP × EP × ETP，DP = `world/(tp·pp·cp)` | `megatron_utils/` 全套 |

**所以「dp+tp+fsdp」在源里不存在** —— FSDP 后端根本没有 TP 参数可传（`run-qwen3-4B-fsdp.sh` 里一个并行轴参数都没有）。
要 TP 就得走 megatron 后端，而 megatron 后端的 DP 是其余轴除剩的，本来就有。**nano 走 megatron 后端（V8 已如此），方向对。**

### 事实二：源在同量级模型上用的是什么

| 源脚本 | 模型 | 卡数 | TP | PP | CP | EP |
|---|---|---|---|---|---|---|
| `run-qwen2.5-0.5B.sh` | 0.5B | — | **1** | 1 | 1 | 1 |
| `run-qwen3-4B.sh` | 4B | 8 | **2**（+SP） | 1 | 1 | 1 |
| `run-glm4-9B.sh` | 9B | 4 | 2 | 1 | **2** | 1 |
| `run-deepseek-r1.sh` | 671B MoE | 多机 | 大 | >1 | >1 | **>1** |

**规律**：TP 只在模型放不下单卡时才开；CP 只在序列长到 `max_tokens_per_gpu` 调不动还 OOM 时才开
（`docs/zh/get_started/qa.md:26` 明说）；EP 只对 MoE 有意义。**0.6B 在源的配方里就是 TP=1 纯 DP。**

### 结论：nano 4 卡的两套配置，分工不同

| 用途 | 配置 | 理由 |
|---|---|---|
| **性能基线**（V9 吞吐要用这个） | **TP=1 × PP=1 × CP=1 × DP=4** | 与源在 0.5B 上的配方一致。0.6B 单卡放得下，任何模型并行都是净亏（多出来的通信换不到显存收益） |
| **教学/验证**（V8.2 的门要用这个） | **TP=2 + `--sequence-parallel` × DP=2**，PP/CP 各单独开一门 | 验的是「切分正确性」不是「跑得快」。TP 组落 GPU0-1 或 2-3（同 NUMA），见 §3.4 |

> **这条必须写进 V9 的结论里**：`0.6B + TP=2` 的吞吐一定**低于** `TP=1`，
> 这是**配置选择的必然结果，不是实现有 bug**。V9 若测出 TP 扩展效率 < 1 就下"TP 实现有问题"的结论，
> 就是把教学配置误当性能配置。**先写下这个预期，再测**（V9 方法学纪律的第一条）。

### 附带落定：`--attention-backend flash` 进 nano 的默认配方

源**所有** megatron 训练脚本的 `MISC_ARGS` 都带这一行。§1.1 实测证明它在 sm_120 上不是可选项而是正确性前提。
nano 的 `MegatronTrainer` 走 TE spec 时应默认 flash，并在 CP>1 时硬断言。

### 顺带修正 §3.3 的实施路径（比原计划更省且更忠实）

源 `model.py:539` 是 `config.finalize_model_grads_func = finalize_model_grads`，
其中 `finalize_model_grads` 直接 **`from megatron.core.distributed import` 进来的原版**（`model.py:14`）——
**源没有自己写 embedding 规约，它用 megatron-core 的**。那份原版已经包含
`_allreduce_word_embedding_grads`（tie 跨 stage）+ `_allreduce_layernorm_grads`（含 qk-layernorm）+ SP/MoE 各分支。

nano 之所以有一份手写的 `_finalize_model_grads`，是 **V8 偏离 #7（用 torch AdamW 而非 `DistributedOptimizer`）的连带后果**
—— 不走 mcore 的 optimizer 就没人替我们调 `finalize_model_grads_func`。
**本版实施时优先尝试直接调用 mcore 的 `finalize_model_grads(model_chunks, config)`**，
调不通再退回手写补 embedding 分支。前者工作量更小、覆盖更全、更忠实源。

## 2. 范围（做什么 / 不做什么）

### 做

- **V8.2.0 · NCCL 后端**（退休偏离 #1）：`MegatronTrainer(backend="nccl")` + 正确的 device 绑定。
  **不是改个字符串就完**——单卡时 `LOCAL_RANK` 恒 0、所有 rank 共用 device 0；多卡必须
  `torch.cuda.set_device(local_rank)` 真绑不同卡（见 §3.1）。
- **V8.2.1 · PP 流水并行**（退休偏离 #3a）：`pipeline_model_parallel_size=2`，
  用 megatron-core 的 `get_forward_backward_func()` 跑 1F1B 调度（**对齐源 `model.py:419-429`**），
  loss 只在 last stage 算（源 `model.py:279`、`loss.py:431`），
  **补 tie 模型的 embedding 梯度跨 stage all-reduce**（源 `finalize_model_grads.py:164`）。
- **V8.2.2 · CP 上下文并行**（退休偏离 #3b）：`context_parallel_size=2`，
  序列按 `cp_utils.get_logits_and_tokens_offset_with_cp` 的 **2-chunk 对称切分**分配到各 CP rank，
  loss 分母按 `get_sum_of_sample_mean` 的 CP 分支修正（源 `cp_utils.py:52-`）。
  **走 TE spec + flash 后端 + THD(packing)**（§1.1 实测：CP 只有 TE 后端支持；flash 后端下 THD 全绿），
  故本刀连带**给 `MegatronTrainer` 加 TE spec 分支**并**硬断言 CP>1 时 attention 后端必须是 flash**
  （落到 fused 上会静默算错 —— 这才是该用断言堵的地方，不是 CP × packing）。
- **V8.2.3 · 组合门**：`TP=2 × PP=2`（4 卡）与 `TP=1 × PP=1`（1 卡）的 fp32 逐值等价。

### 不做（登记为偏离，理由充分）

- **EP 专家并行**：Qwen3-0.6B 是 **dense 模型，没有 expert**。开 EP 是空转，不是「做不到」而是「无对象」。
  换 MoE 模型（如 Qwen3-30B-A3B）才有意义，超出本项目模型规模。
- **虚拟流水（VPP / interleaved 1F1B）**：源支持 `virtual_pipeline_model_parallel_size`。
  它是**减小 bubble 的调度优化**，不改变 PP 的语义；4 卡 2 stage 的 bubble 本就不严重。
  留给 V9 作为吞吐旋钮之一（**V9 正是量化 bubble 的地方**）。
- **`DistributedOptimizer`**：维持 V8 偏离 #7（torch AdamW）。它是 ZeRO-1 式**优化器状态分片**，
  与 TP/PP/CP 正交、属于「省显存」而非「并行语义」，铺开会冲淡本版主线。
- **Ray 闭环**：维持 V8 拍板（与 V7.3 高度同构）。本版仍用 `torchrun` 验收。

## 3. 五个必须做对的正确性点（源级锚定）

> 这一节是本计划的核心。每条都标了源位置——**写码前先读源那一段**（铁律）。

### 3.1 device 绑定：`LOCAL_RANK` 从「恒 0」变成「真 rank」

V8 单卡时写的是「所有 rank 共用 device 0」（`megatron_trainer.py:127-130` 有注释说明，
与 V7.3 的 Ray 场景同理——那里 Ray 独占 `CUDA_VISIBLE_DEVICES` 所以 `LOCAL_RANK` 恒 0）。
**多卡 torchrun 下这个前提反转了**：`torchrun --nproc_per_node=4` 会给每个进程发不同的 `LOCAL_RANK`，
必须 `torch.cuda.set_device(local_rank)` 真绑不同卡，否则 4 个进程全挤在 GPU0 上 → 立刻 OOM，
且 NCCL 会以 `Duplicate GPU detected` 拒绝。

**现有代码已经写对了**（`local_rank if local_rank < device_count else 0`）——单卡时 fallback 到 0，
多卡时用真 rank。本版只需**验证**这条分支，并把注释里「单卡」的措辞改成两种情形都覆盖。

### 3.2 PP 的 1F1B 调度：**必须用 `get_forward_backward_func()`，不要手写**

源 `model.py:419-429`：

```python
forward_backward_func = get_forward_backward_func()
losses_reduced = forward_backward_func(
    forward_step_func=forward_step, data_iterator=data_iterator, model=model,
    num_microbatches=num_microbatches, seq_length=args.seq_length,
    micro_batch_size=args.micro_batch_size, forward_only=False)
```

megatron-core 会按 `pp_size` 自动选 `forward_backward_no_pipelining` /
`forward_backward_pipelining_without_interleaving`（1F1B）。**手写 send/recv 调度是重复造轮子且必错**
（1F1B 的 warmup/steady/cooldown 三段、以及跨 stage 的梯度累积边界很容易搞反）。

**对 nano 的结构影响**：`_microbatch_backward` 现在是「自己 forward + 自己 backward」。
接 PP 后要拆成源的两件东西：
- `forward_step(data_iterator, model) -> (output_tensor, loss_func)`：只做前向，返回 logits + 一个偏函数；
- `loss_func(output_tensor) -> (loss, metrics)`：算 GRPO loss（`_grpo_sample_loss` **一行不改**）。

这不是为 PP 特设的改造——**源本来就是这个形状**（`model.py:380-416` 的 `forward_step` +
`loss.py` 的 `loss_function`）。V8 因为 PP=1 才能偷懒合成一个函数，登记为本版要还的技术债。

### 3.3 **PP + tie：embedding 梯度必须跨 first/last stage all-reduce（本版最硬的正确性点）**

Qwen3-0.6B `tie_word_embeddings=True`（V7.0 已实测确认）。PP>1 时：
- **first stage** 持有 `embedding.word_embeddings.weight`（输入嵌入）
- **last stage** 持有 `output_layer.weight`（输出投影）
- tie 意味着**这两个是同一份权重**，但它们物理上在**不同的 stage、不同的进程**里。

各自算出的梯度都只是**部分和**，必须跨 first/last stage all-reduce 才是全量。
源 `finalize_model_grads.py:164` `_allreduce_word_embedding_grads` 做的正是这件事，
用的组是 `mpu.get_embedding_group()`（**§1 实测 = `[0, 1]`，通路已就位**）。

> **这与 V8 的坑 3 是同一类错误、同一个指纹**：V8 漏了 qk-layernorm 的 TP all-reduce，
> 表现为「前向 loss Δ 恰为 0、梯度却系统性偏 1.8e-2，最差参数正是 `q_norm.weight`」。
> PP+tie 漏规约会给出**一模一样的指纹**，只不过最差参数变成 `embed_tokens.weight`。
> **fp32 精确门能抓到、bf16 抓不到**（V8 已证：5e-2 会被当舍入放过）。
> 所以本版**必须跑 fp32 档**，不能只跑 bf16。

nano 的 `_finalize_model_grads` 目前只有 qk-layernorm 一条分支（V8 偏离 #6，理由是「PP=1 故无跨 stage 规约」）。
**本版要补上 embedding 分支**，该偏离随之部分退休。
**但实施路径首选不是手写** —— 源直接用 megatron-core 的原版 `finalize_model_grads`（它已含此分支），见 §1.5 末节。

### 3.4 rank 映射要贴合拓扑：**TP 放 NODE 内，PP 跨 NODE**

Megatron 的 rank 布局顺序是 `tp → cp → dp → pp`（`mpu.initialize_model_parallel` 的默认 order）。
结合 §1 实测拓扑（0-1 同 NUMA、2-3 同 NUMA、跨组 SYS）：

- **TP 通信量最大**（每层两次 all-reduce 激活）→ 必须放**同 NODE 内**（GPU0-1 或 GPU2-3）
- **PP 通信量最小**（每 stage 边界一次 p2p，只传一份激活）→ **跨 NODE 可接受**

`TP=2 × PP=2` 的默认布局恰好是 `[0,1]` 一个 TP 组、`[2,3]` 另一个 TP 组，PP 跨组——**正好对**。
本版要在验收里**显式打印并断言** `get_tensor_model_parallel_group()` 的 ranks 落在同 NODE 内，
把「拓扑感知的 rank 映射」变成可验证的知识点而不是口头常识。

### 3.5 CP 的序列切分是 **2-chunk 对称**，不是朴素均分

源 `cp_utils.py:29-31`：

```python
chunk_0 = (cp_rank * chunk_size, (cp_rank + 1) * chunk_size)
chunk_1 = ((2 * cp_size - cp_rank - 1) * chunk_size, (2 * cp_size - cp_rank) * chunk_size)
```

每个 CP rank 拿**两块**：一块靠前、一块靠后（对称位置）。**为什么不朴素均分**：
因果 attention 下，靠后的 token 要 attend 前面所有 token，工作量随位置线性增长。
朴素均分会让最后一个 rank 干最多活、其余空等（负载严重倾斜）。
2-chunk 对称切分让每个 rank 的 (前块轻 + 后块重) 之和相等 —— **这是 CP 的精华，必须忠实复现**。

连带影响 loss 分母：`get_sum_of_sample_mean` 在 CP>1 时要跨 CP 组规约
（每个 rank 只见部分 token，`loss_mask.sum()` 是部分和）。源 `cp_utils.py:52-` 已给出完整实现。

## 4. 验收设计（沿用 V8 已打磨好的分层 gate，度量代码不改）

**V7.5 的度量教训继续适用**：全局 rel_L2 + cosine（向量级、大信号主导），
不用逐参数 max（小信号参数的 bf16 噪声会虚高）；**fp32 才是精确证明，bf16 只到舍入**。

| 门 | 配置对比 | 卡数 | 判据 | 抓什么 |
|---|---|---|---|---|
| **G1 NCCL 基线** | NCCL TP=2 vs **V8 已存的 gloo TP=2 dump** | 2 | fp32 loss Δ<1e-4、rel_L2<5e-3、cosine>0.9999 | 换后端不改数学 |
| **G2 PP** | `TP=1×PP=2` vs `TP=1×PP=1` | 2 | 同上 | **§3.3 的 embedding 漏规约**（指纹：loss Δ=0 但 `embed_tokens.weight` 梯度偏） |
| **G3 CP** | `CP=2` vs `CP=1`（**TE spec + flash 后端 + THD(packing)**，见 §1.1） | 2 | 同上 | §3.5 切分与 loss 分母 |
| **G4 组合** | `TP=2×PP=2` vs `TP=1×PP=1` | **4** | 同上 | 三轴组合无交叉污染 |
| **G5 拓扑** | 打印各并行组 ranks | 4 | TP 组落在同 NUMA node 内 | §3.4 |
| **G6 转换** | `to_hf_state_dict()` 在 PP>1 下往返 | 4 | `max_abs_diff==0` | **PP 下权重分散在多 stage**，转换要先跨 PP broadcast（源 `hf_weight_iterator_direct.py:66-77`） |

**G6 值得单独说**：V8.1 的转换只处理了 TP-gather，因为 PP=1 时**一个 rank 持有全部层**。
PP>1 时 layer 0-13 在 stage0、layer 14-27 在 stage1，**任何单个 rank 都拿不到完整模型**。
源的做法是 `broadcast params across pp ranks`（`hf_weight_iterator_direct.py:66-77`）。
这是「Megatron→HF 转换」这条 RL 接缝在多维并行下的**真实复杂度**，V8.1 只见到了它的一半。

**回归**：V8 的全部门（fp32 4 层 / fp32 28 层 / bf16 / V8.1 TP=1,2）+ V7.5/V7.6 + 离线 V0–A3 全绿。
**新代码全部走 opt-in 参数**（`pipeline_model_parallel_size` / `context_parallel_size` 默认 1、
`backend` 默认保持 `"gloo"` 以免单卡回归被破坏），保证零回归。
