# 边缘部署的资源权衡（设计记录，非本项目复现范围）

> 状态：**设计留档，不实现**。本项目当前硬道理是**复现原项目、学习主线**（主线一 ✅ / 主线二 A2 进行中）。
> 本文只记录一次关于"训好规划器 + 专家模型包装成工具"后如何在受限边缘设备部署的推演，供 A3 ToolOrchestra
> （多专家路由 + 成本/延迟 reward）和主线三（rollout/train 分离）到时对照。**它不改变复现优先级，也不进任何验证脚本。**

## 起点：架构哲学（用户提出，本文采纳）

不训练一个通用大模型，而是：**训练一个规划模型（planner）+ 后续按需训练专门的小模型，包装成工具**
（工具内部可再调模型，即 agent 形态：code agent、search agent……）。每个专家可独立训练、独立升级。

这正是主线二的演进方向：
- **A2 AgentFlow**：planner 训"规划"，executor/工具**不训练**（工具边界）。
- **A3 ToolOrchestra**：orchestrator 路由到多专家，reward = 正确性 + **成本 + 延迟**——本质在奖励
  "能用便宜/确定的工具就别调大模型"。**本文的部署结论就是这条 reward 在部署层的镜像。**

## 约束

- 模型**云端训练**、**边缘部署**；边缘显存上限 **64G**（含 KV cache）。
- 训得起的最大模型 **7B**。算上 KV cache，同时常驻 **≈3 个模型**是实际上限。
- 原始问题：**3×7B 好，还是 1×7B + 2×3B 好？规划器 3B 还是 7B？**

## 关键区分：训练端 vs 部署端是两笔账

| | 训练端（云） | 部署端（边缘 64G） |
|---|---|---|
| 谁吃显存 | **只有被训练的那个模型**（权重+优化器态+梯度+激活） | **所有常驻模型同时占用**（权重 + KV cache） |
| 专家模型 | 训 planner 时它们**冻结当环境工具**，可放别的卡/节点 | 必须随时响应，全部常驻 |
| 结论 | 三模型**分阶段独立训**，不必同批显存 | 要算**并发驻留总显存** |

因为三个模型独立训练（planner 训规划、专家各训各的），云端可分阶段：
先训 7B planner（专家用现成模型当冻结环境）→ 再各训专家 → 专家变强后可回炉再训 planner 适应。
这正对应 slime 里 rollout engine 与 train actor 分离的架构（主线三 V6 复现点）。

## 显存粗算（BF16 推理驻留：7B≈14G / 3B≈6G）

| 方案 | 权重 | KV cache 余量（64G−权重） | 评价 |
|---|---|---|---|
| 3 × 7B | ~42G | ~22G | 紧，长上下文 KV 吃紧 |
| 1×7B + 2×3B | ~26G | ~38G | 宽松 |
| **1×7B + 1×3B（本文最终，见下）** | **~20G** | **~44G** | 砍掉 code 模型后最宽松 |

（若 INT8/FP8 量化部署，权重再砍约一半，各方案更宽松。）

## 分配原则：参数花在"需要开放泛化"的角色

显存只是约束，不是目标。按**能力密度**分参数——任务越需要开放泛化，越值得大模型。

| 角色 | 任务 | 难度 | 该多大 |
|---|---|---|---|
| **Planner（被训练）** | 理解问题→分解子目标→选工具→判断何时停 | 最高（要泛化到没见过的任务组合） | **7B** |
| **Code 专家** | 见下——用户实际需求只是文件处理/跑脚本 | 低 | **0 模型 · skill/脚本** |
| **Search 专家** | 检索 + 抽取 + 综合 | 中（受限子任务，但有长上下文问题） | **3B + 检索管线** |

### Code：不该是模型

用户实际需求是"文件处理这类工作，甚至写个 skill 给几个脚本让其运行即可"。结论：**做成确定性工具，不用模型。**
- 文件处理/跑脚本用 LLM 写代码反而引入不确定性（写错、幻觉路径）。预置脚本 + 明确入参，planner 只负责
  "选哪个脚本、传什么参数"，执行确定、可审计、快。
- 直接省掉一整份显存（3B 权重 + 其 KV cache）。
- 这正是 A3 的核心洞察：**工具不必是 LLM**；orchestrator 路由的"专家"有的是模型、有的是普通函数。

### Search：瓶颈是架构分段，不是模型大小

长上下文有**两个独立问题**：
- **A. KV cache 显存**：长上下文时小模型更省（KV ∝ 层数×hidden_dim）。但一个 3B 跑 32K 上下文，KV cache
  可能十几 G > 其 6G 权重——所以要给它留足 KV 预算（砍掉 code 模型省下的显存正好喂这里）。
- **B. 小模型能否"读懂"长上下文**：**换大模型解决不了、也不该靠换大模型。** 正确架构是
  **检索 → 压缩 → 推理**三段（map-reduce）：
  1. 检索：确定性工具（BM25/向量库）返回候选片段——不吃模型。
  2. 压缩：小模型**分块**把每段缩成要点（每次只看一小段，上下文永远短）——map。
  3. 综合：模型只在**压缩后的短上下文**上综合——reduce。
  这样"3B 上下文够不够"在很大程度上消失（每次喂的都短）。**3B + 好的 map-reduce 管线，通常胜过
  7B + 把原文一次性灌进去的裸方案。**

## 最终建议

| 角色 | 方案 | 显存 |
|---|---|---|
| Planner | **7B**（唯一需要开放泛化，省它最不划算） | ~14G |
| Code | **skill/脚本，0 模型** | 0 |
| Search | **3B + 检索/压缩(map-reduce)管线** | ~6G + 充足 KV |
| 合计 | | ~20G 权重，**~44G 全给 KV** |

**升级路径**（按需，不预支）：若 search 的**综合**环节确实吃力（多跳、跨片段推理），把 search 升到 7B
（7B planner + 7B search + skill code = 28G，仍 < 3×7B 的 42G），**而不是**去堆上下文长度。

**不推荐 3×7B**：只有当三个角色都需开放泛化才值得——但那就退回"三个通用大模型"，违背"专家专精"初衷，
且 KV 余量最紧。

## 一句话总纲

**参数花在需要开放泛化推理的地方（planner，可能还有 search 的综合）；能确定性化的一律确定性化（code）；
长上下文用架构分段（map-reduce）解决，而不是用大模型硬扛。**
