# 07 · 怎么选配置：三步决策法与 benchmark 的教训

> 对应原文：Finding the Best Training Configuration / Benchmarking thousands of configurations / Lessons learned on benchmarking

---

## Step 1：先让一步训练**装得下**

### GPU 富裕 🤑

- **< 10B**：单一技术就够——比如 8 卡上用 TP，或 ZeRO-3/DP + full 重算。
- **10B–100B**（需要 >8 卡）：三选一
  - TP=8 + PP
  - TP=8 + DP(ZeRO-3)
  - 纯 ZeRO-3
- **512+ 卡**：纯 DP/ZeRO-3 因通信成本开始低效 → 应该配上 TP 或 PP。
- **1024+ 卡**：推荐 **TP=8 + ZeRO-2 + PP**。

**特殊情况**：超长序列 → **跨节点加 CP**；MoE → **跨节点加 EP**。

### GPU 贫穷 😭

- 开 **full 激活重算**（拿算力换显存，训得慢一点）；
- 加 **梯度累积**，用有限显存吃更大的 batch。

---

## Step 2：打到目标全局 batch size

**要调大**：加 DP 或加梯度累积步数；长序列场景可以用 CP。
**要调小**：减 DP、把并行换到别的维度；长序列可以减 CP。

---

## Step 3：优化吞吐

只要显存和通信还不是瓶颈，依次尝试：

1. **先把 TP 拉到接近节点大小**（吃节点内高速带宽），从而减少其它形式的并行；
2. 在保持目标 batch size 的前提下**用 ZeRO-3 加大 DP**；
3. **当 DP 通信开始成为瓶颈时，转用 PP**；
4. 逐个维度扫；
5. **调 mbs**，在最大 gbs / 模型大小 / 计算 / 通信之间找平衡。

---

## 上千个配置的实测结论

作者在 **1–64 个 8×H100 节点**上跑了数千个分布式配置（seq=4096、gbs=1M tokens），做成热力图（颜色深浅 = MFU）。三条洞察：

1. **节点越多、效率越低**，**小模型尤其明显**（计算量 / 模型大小比值低）。通常可以靠加 batch 补偿，但**受 gbs=1M 的上限约束**。
2. **大模型的困境相反**：节点少时要么根本装不下，要么装下了但**贴着显存上限跑，效率很差**（例：80B 模型在 4 节点上）。
3. **性能高度依赖实现质量**——这条最值得记住：
   > 他们最初实现时 **TP 快于 PP**；**优化了 PP 代码后 PP 反超**；现在又在改进 TP 的通信重叠，预期 TP 会再次领先。

   **也就是说"TP 和 PP 谁更快"这个问题，很大程度上量的是你自己代码的成熟度，而不是两种并行的固有性质。**

## Benchmark 工程上的血泪教训

纸面上很简单（往集群上撒一堆 job），实际一开跑就出问题：

- PyTorch 进程有时**不能正常清理**；
- Slurm 强杀 job **导致节点故障**；
- 本该几分钟的简单 benchmark **拖成几小时**；
- 有些 job **无限 hang**。

为了在有限时间内跑完，他们额外花了大量精力在：

- 最小化集群重启时间、压缩空转；
- 分析详细的 **NCCL debug 日志**；
- 理解**显存使用模式和 CUDA 内存分配器行为**；
- 改进**多节点下的 PP 性能**。

> 原话的总结：**理论上简单的东西，实践中需要照顾大量活动部件。**

## 一个必须记住的前提裂缝：重叠不是免费的

全书前面反复依赖一个假设：**计算与通信可以高效重叠、且不影响计算吞吐**。**现实更微妙**：

> 用 NCCL send/recv 这类常见原语时，**通信 kernel 通常会占用与计算相同的 SM**（streaming multiprocessor）。这会导致**通信与计算重叠时计算吞吐下降**——存在隐性的资源争抢。

另外，重叠时的同步模式对某些并行策略未必最优。

**这就是为什么要往下钻到 GPU 架构内部**（见 [08](08-gpu-internals.md)）。

## 与本项目（V9）的关系

这一章基本可以直接当 **V9 的方法论对照表**：

1. **「性能高度依赖实现质量」这条对 V9 的解读纪律至关重要**：nano 若测出「Megatron TP 比 FSDP 快/慢」，**不能**得出关于两种并行本身的结论——只能说 nano 这两份实现在这台机器上的表现。V9 的结论措辞必须收在这个边界内。
2. **「重叠会抢 SM」这条给了 V9 一个可预先写下的预期**：nano 目前 DP 通信没有重叠（没有 bucketing/hook），所以**不会**观察到这种争抢；但一旦以后加了重叠，**吞吐提升会低于「通信时间完全消失」的理论值**。先写下来，免得将来测出来再编解释。
3. **benchmark 工程教训对 V9 的执行直接有用**：hang、进程不清理、共享 GPU 上数字不可比——CLAUDE.md 里 V9 纪律那条「必记 `nvidia-smi` 快照」和这里是同一个问题。
4. Step 3 的顺序（**TP 先拉满节点内 → 再加 DP → DP 撞墙才上 PP**）可以作为 V9 扫参数的**扫描顺序**，而不是盲目全组合——4 卡机上完整笛卡尔积没意义。
