# 通用技术学习笔记（learning-notes）

> 本文件是一份**方法论 skill**：定义「如何把一个看不懂的技术对象变成一份可复用的图文学习文档」。
> 参考 `reading-large-codebases` 的格式与纪律，但把适用对象从「大代码库」泛化到四类：
> **代码/方法、系统/框架边界、概念、公式↔代码**。
> 存放于项目 `docs/` 下，作为项目内约定维护；如需全局使用，可原样迁移到 `~/.claude/skills/learning-notes/SKILL.md`。

## 用途（什么时候触发）

用户想 **理解任何一个"看不懂"的技术对象**，且希望产出**一份持久化的图文笔记**（不是口头回答）时使用。典型触发词：

- "把这个概念讲透 / 整理成 md / 写篇学习笔记 / 讲一下这个系统怎么工作的"
- "分析一下这个框架代劳了什么、我要负责什么"（边界分析）
- "把公式逐条对上代码，证明没算错"（公式↔代码对照）
- "帮我读一下 X.py / 这个项目怎么入门"（代码/方法）

产出是一份**学习文档（带编号图）**，不是代码改动。若要重构代码，用 `plan`；若要找某符号定义，用 `Grep`/`Explore`。

本仓库的既有实例（风格对齐对象）：

- 系统/边界型：`docs/test-learn/code-read/tp-megatron-calling-boundary.md`（Megatron 代劳 vs 调用方负责）
- 公式↔代码型：`docs/grpo-formula-to-code.md`（GRPO 公式逐条对两边代码）
- 概念型：`docs/tied-word-embeddings.md`（是什么 → 怎么判断 → 怎么验证）
- 代码/方法型：`reading-large-codebases` 的产物（骨架 → 热点 → 编号图 → 散文）

## When NOT to use

- 用户只要一句话答案 → 直接答，别产出文档
- 对象很小（<300 行或单一概念）**且**没有层次/边界/多阶段 → 内联讲清楚即可
- 用户要的是架构方案 / 重构方案，不是解释 → 用 `plan` / `spike`
- 任务是"X 定义在哪" → 这是查找，用 `Grep` / `Explore`

注：行数/体量只是启发，不是闸门。一个 190 行的函数、一个一句话能说的概念，如果**概念密度高**（7 层装配、跨进程边界、隐含假设），仍然值得一篇文档。

## 核心方法

四个阶段，**逐阶段把关**，跳步会产出与事实不符的图：

```
  建坐标系  →  找核心  →  编号图  →  1:1 散文
      ↑                                  ↓
      └──────── 图对不上就回头重读 ────────┘
```

### 阶段 1：先建坐标系（不要线性读）

对**任何对象**，先别从头读到尾，先按对象类型找 landmark：

| 对象类型 | 坐标系怎么建 |
|---|---|
| 代码/方法 | `wc -l`、`grep -nE "^class \|^def "`、`grep -n "while \|for .* in "` → 骨架表 |
| 系统/框架 | 谁调用谁 / 输入输出边界 / 进程与拓扑 / 状态何时离开系统 / 装配阶段 vs 调用阶段 |
| 概念 | 「定义 / 判断依据 / 操作步骤 / 边界条件」四大件，缺一不可 |
| 公式 | 符号表 / 假设 / 推导步骤 / 聚合规则（组内 vs 组间、mask 位置） |

把骨架**表格化**（这是文档 §2 的内容）：

| 区域 | 位置（行号/小节） | 作用 |
|---|---|---|
| imports / 背景设定 | 1–N | ... |
| 核心机制 | N–M | 值得研究的部分 |
| 边界/收尾 | M–… | 框架代劳之外调用方要做的 |
| 入口 / 触发路径 | last | 怎么被用起来 |

### 阶段 2：找核心（3-5 个热点）

在各对象里找真正重要的 3-5 个点，只深读这些：

- **主循环 / 核心机制**：几乎总是理解的入口
- **调度 / 分派**：多态、路由、hook 拦截住在这里
- **接口 / 序列化边界**：外部世界看到什么（参数、schema、返回格式）
- **副作用 / 持久化**：状态何时离开进程
- **边界线**（系统/框架型）：框架自动做的 vs 调用方必须负责的 —— 这是本类笔记的灵魂
- **关键等式与聚合**（公式型）：哪一步等价、哪一步是外围差异
- **验证步骤**（概念型）：配置判断 → 实际参数验证 → 运行时断言

其余部分要么是被热点调用的辅助，要么是防御性代码（重试/修复/sanitize），**列成表**即可，别逐行走。

### 阶段 3：编号图（纪律最严格，别在这偷懒）

> **图中每个节点必须有对应编号段落；散文里提到的每个函数/符号必须出现在图里。**
> 读者指着节点你无话可说，或指着段落找不到节点，图就是坏的。

**Mermaid 纪律（全保留）：**

- **节点 ID 必须线性，不许用语义 ID 当主锚**。节点标签以 ❶❷❸… 开头；语义名放**标签内部**：
  `❹ _vocab_parallel_log_probs<br/>TP 组内规约 softmax` ✓
  禁止 `P1`/`AGENT`/`DISP` 这种无顺序信息的 ID ✗
- **跨节共享坐标**：后一节展开前一节某节点时，复用父编号加子字母：❹a、❹b、❹c。绝不另起一套 `autonumber` 1–13。
- **独立序列图才可用 `autonumber`**；凡是"展开上级某节点"的序列，必须手写 ❸/❹a/❹b 到消息标签里。
- **分阶段 subgraph**：装配(一次) / 调用(每次)、startup / steady-state、build-time / runtime 必须分开子图，别把一次性箭头和每轮箭头混在一张平图里。
- **节点标签带真实标识符**：`"⑨ _allreduce_qk_layernorm_grads()<br/>TP 组内 SUM"` —— 读者能直接 grep 源码。
- **图前必须有 framing**：画图前先写 1–3 句"问题是什么、答案一句话是什么"。图冷启动=读者瞎猜。
- 标签用 `<br/>` 叠短语；`>`/`<` 用 `&gt;`/`&lt;`；HTML 敏感字符加引号。

图的数量按对象复杂度定：概念型常 1–2 张（概念地图 + 验证流程）；系统/边界型常 2–3 张（装配/调用 两阶段 + 边界线）；公式型常 1–2 张（对照关系图）；大代码库型 3–4 张（全貌 / 主循环 / 分派 / 端到端）。

### 阶段 4：1:1 散文

**开篇先问，别先给图**。mermaid 块前写 1–3 句：这里原本让人困惑什么、答案是什么、图要解决什么。

每张图下面按编号逐节点写段：

```markdown
**图解（严格按 ❶~❻ 顺序读）**：

**❶ <节点标签>** —— <1–3 句：做什么、为什么存在、与相邻节点关系>（[megatron_trainer.py:208](../../toy_rl/trainer/megatron_trainer.py#L208)）

**❷ <节点标签>** —— <…>（[file.py:LINE](../../相对路径#LLINE)）
```

**规则：**

- **散文顺序 = 图编号顺序**，无例外。写 ❶→❷→❸，绝不跳。若图允许非线性读，是图错了，改图不改散文。
- **一节点一段、一段一节点**。别合并、别拆散。
- **段落首粗体必须与图 marker 完全一致**：图中 ❶ → 散文 `**❶ ...**`。
- **写 why，不写 what**：代码里已有的"调用 foo 再调 bar"别复述；讲清顺序背后的约束或踩过的坑。
- **带真实标识符**（`_allreduce_qk_layernorm_grads`、`parallel_output`），保证可 grep。
- **文字说明必须附带代码跳转**：每个关于实现的说法都要能**点一下跳到源码**，用 markdown 链接 `[file.py:LINE](../../相对路径#LLINE)`，不要裸写 `file.py:1234`。示例：`[megatron_trainer.py:208](../../toy_rl/trainer/megatron_trainer.py#L208)`（相对路径从笔记所在目录起算，`docs/skill/` 或 `docs/code-read/` 下都只需 `../../` 上溯两级到仓库根）。
- **每图结尾一行"关键直觉"**：整图守护的不变量，能命名成可复用模式就命名（如"TP 边界 = 层内切分归框架 + 梯度收尾归调用方"）。
- **禁止"对照 §X 的图"footer**：跨节引用走共享节点 ID，不走"A 在 X 框里"这种会腐化的措辞。

## 文档模板

### 通用头（每篇必写）

> **目的**：<what —— 一句话说明这篇讲什么>，以及 <why —— 哪个设计约束/边界/坑让它在乎>。全文/对象 ~N 行（L起–L止），骨架是 <structure>。

```markdown
> **目的**：讲清 `MegatronTrainer` 开 `--tp 2` 后，层内权重切分与主通信由 Megatron Core 代劳，
> 调用方只需负责并行拓扑、模型/损失接缝与训练系统外部的权重流转。全篇 ~200 行，骨架是
> 1 张装配图 + 1 张调用图 + 1 条边界线。
```

### 变体 A：系统/框架边界型（对齐 `tp-megatron-calling-boundary.md`）

```markdown
# <主题>：<框架> 代劳什么，调用方负责什么

> **目的**：<what + why + structure>

## 〇、一张图看全貌
<装配阶段 + 调用阶段 两子图>
<prose>

## 一、它是什么 / 一次真实运行
<最小可运行入口：命令 + 关键参数怎么进代码>

## 二、<框架> 自动完成的部分
| 模块 | 切分方式 | 运行时结果 |
|---|---|---|

## 三、调用方仍然必须负责的部分
### 3.1 进程与拓扑
### 3.2 自己的训练语义（callback / loss / optimizer）
### 3.3 裸模型路径需要的少量收尾

## 四、不要和主路径混淆的代码
<转换脚本、测试代码 —— 它们也做 TP 通信，但不是训练主路径>

## 五、最小心智模型
<5-8 行可运行骨架代码>

## 六、本仓库的范围
<实现了什么 / 没实现什么（如 EP/SP）>

## 七、建议阅读顺序
```

### 变体 B：公式↔代码对照型（对齐 `grpo-formula-to-code.md`）

```markdown
# <公式> 公式 ↔ 代码对照

> **为什么写**：nano 的实现（<文件>）和 <另一份熟悉实现> 写法很不一样，看不懂。
> 本文把 <公式> 逐条对上两边的代码，证明没算错。

## 0. 先说清两份代码的"身份"
| 维度 | 实现 A | 实现 B |
|---|---|---|
| 锚点 / 变体 | ... | ... |
| 归一 | ... | ... |
| 差异点 | ... | ... |

## 1. <公式> 的数学（双方共同遵守的）
<逐条列出核心公式，标注聚合规则>

## 2. 逐条对上代码
### (a) <公式名>
**实现 A**（文件:行号）+ 代码块
**实现 B**（文件:行号）+ 代码块

## 3. 结论
<核心数学等价，差异全在外围>
```

### 变体 C：概念型（对齐 `tied-word-embeddings.md`）

```markdown
# <概念>：判断与验证说明

## 1. 什么是 <概念>
<定义 + 数据流图（ASCII/mermaid）+ 收益与约束>

## 2. 如何判断
### 2.1 加载前：检查配置
### 2.2 加载后：验证实际参数
### 2.3 运行时：<必要时>断言

## 3. 工程影响 / 踩坑
```

### 变体 D：代码/方法型（= `reading-large-codebases` 模板）

沿用其完整模板（目的行 / 一张图看全貌 / 文件骨架 / 职责分层 / 端到端真实请求 / 接下来看什么 / 读源码提醒），不在此重复。

## 反模式（觉得对但浪费读者的事）

- **一堆 bullets 代替图**：能画就画，文字丢空间关系。
- **图的标签是泛称**（`Process`、`Handler`、`框架层`）：必须用真实函数名/符号/等式。
- **语义 ID 当主锚**（`P1/AGENT/FRAMEWORK`）：读者不知道先后，散文被迫自造顺序。
- **每节独立编号 + 底部"对照 §X 的图"footer**：§A 一改，§B 的 footer 就指向空。用共享节点 ID（❹a/❹b）。
- **一次性箭头与每轮箭头混在一张平图**：读者按从上到下当时间线读，全错。用 subgraph 分阶段。
- **散文复述代码**（"调 A 再调 B"）：讲 why，或者删掉。
- **编造函数名**：没读过的行不要写进图/散文。写前 `grep -n` 确认每个标识符存在。
- **巨型单图（40 节点）**：拆成 happy path + error recovery 两张。
- **图散文双份重复**：选一个，通常"编号图+编号散文"取代纯文字复述。
- **无坐标的断言**：每个关于代码/公式的说法要可核对，必须带**可点击的代码跳转链接**（`[file.py:LINE](../../相对路径#LLINE)`）；裸 `file.py:1234` 读者没法点，不算。
- **图冷启动**：每张图前 1–3 句 framing。
- **边界笔记里混进"权重转换/测试代码"**：它们也做 TP 通信，但不是训练主路径 —— 放专门一节"不要混淆的代码"，别并进主流程（见 `tp-megatron-calling-boundary.md` §4）。

## 验证清单（宣布完成前过一遍）

1. **线性节点 ID**：每节点以 ❶❷❸… 开头，无 `P1/AGENT/STEP_FOO`。
2. **跨节坐标一致**：后节展开前节节点时，复用父编号 + 子字母（❹a/❹b）；不新开 `autonumber`。
3. **无 framing-language footer**：搜"对照 § / 在 X 框里"，有则换成共享节点 ID。
4. **节点覆盖**：每个图节点都有编号段落；散文提到的每个标识符都在图里。
5. **散文顺序 = 图顺序**：读 ❶❷❸ 是否顺畅；若被迫 ❶→❸→❷，改图。
6. **图前 framing**：每图都有 1–3 句"解决什么问题"。
7. **Grep-ability**：随机挑 3 个函数名 `grep -n` 源码，应命中。
8. **代码跳转可点且行号准确**：每条 `[file.py:LINE](../../相对路径#LLINE)` 的相对路径正确、行号经 `grep -n "def <name>"` 校准未漂移。
9. **Mermaid 能渲染**：粘到 mermaid.live 检查解析错误；未转义 `<`/`>`/`|` 是头号静默失败。
10. **读者测试**：只看图能讲出大致故事吗？只看散文能跟上吗？任一不行就补。

## 交互原则

- **阶段 1 之后先亮骨架**：一条消息给出骨架表 + 核心选择，问"要不要换掉某个再画"。别直接画出讲错对象的文档。
- 收到"看不懂 A→B / 图里没有 X"的反馈时，修法是**加节点编号 + 配对段落**，不是加更多散文。
- 用户是在学项目（不是学单个文件）时，文末给 §"接下来看什么"：3-5 个相邻文件的单行钩子。这是让 explainer 变成 skill 而不是报告的关键。

## 工具配方

```bash
# 阶段 1：代码对象
wc -l path/to/file.py
grep -nE "^class |^def " path/to/file.py
grep -nE "    def |    async def " path/to/file.py | head -200

# 阶段 1：系统/框架边界 —— 找出"谁在装配、谁在调用、边界在哪"
grep -n "init_process_group\|initialize_model_parallel\|_build_\|parallel_output" 相关文件
grep -n "def forward_step\|def loss_func\|def train_batch" 相关文件

# 阶段 3：命名节点前先确认标识符存在
grep -n "def _allreduce_qk_layernorm_grads\|def _vocab_parallel_log_probs" toy_rl/trainer/megatron_trainer.py

# 阶段 5：写完后验证每个命名函数
grep -n "_finalize_model_grads\b" toy_rl/trainer/megatron_trainer.py
```

大文件/大系统直接派 `Explore` 子代理做窄问询（"列出 AIAgent 上所有 `_execute` 开头的方法"），别把上万行灌进上下文。
